一、架构决策

在 V4.1 的采集主干上增加竞争情报模块。继续使用本机 Windows、Python、SQLite、原文归档、版本记录、执行锁、每日三次调度和遗漏补采。自建竞争关系、事件归并、目标关联、证据查询这部分业务能力；网页抓取优先复用已有依赖，动态网页按需增加 Playwright。

新模块应回答五个问题：
1. 目标公司的哪些业务，与哪些主体在什么范围内竞争？
2. 这些竞争者有哪些可持续监测的公开或已授权来源？
3. 最近发生了哪些有证据的变化？
4. 这些变化为何与目标公司的具体业务有关？
5. 哪些资料未取得、身份未确认、范围不明确或结论尚待核验？

系统是可配置的通用机器。新增公司、竞争者、官网入口、行业规则包应通过配置与数据完成；特殊网站需要适配时，扩展通用适配器或声明能力缺口，不把公司名称、财务答案、竞争关系答案写进生产逻辑。

本轮完成监测和研究信息输出，不把竞争事件直接转换成交易指令。自动发现可以给出候选；对“存在竞争”的确认和对“产生财务影响”的判断分别建模。

二、开源方案调查与取舍

以下核查的是截至本设计日期的官方仓库和文档，没有安装实测这些项目，也不据此承诺生产可靠性。

1. changedetection.io
   能力：网页变化检测、选择器、浏览器步骤、历史快照与差异、REST API；适合产品、价格、公告和业务介绍页。
   许可证：Apache-2.0。官方有 Windows pip 安装说明，动态抓取需要浏览器组件。
   决策：作为未来可选的网页监测服务；第一期不设为强依赖，因为现有项目已经有调度、抓取、原文和版本管理。
   接入时只经适配器读取检查结果，不让它写主库。保留外部任务、检查时间、快照身份和内容证据；不得在发现变化后只重新抓一次当前页面，就宣称取得了原先变化的前后证据。外部快照不足时明确标记。
   如果启用其自主调度，必须明确由谁拥有每个 endpoint 的检查权，避免本机调度与外部调度重复抓取。API 触发成功只表示已排队，必须检查实际完成与超时。
   来源：https://github.com/dgtlmoon/changedetection.io
   来源：https://changedetection.io/docs/api_v1/
   来源：https://github.com/dgtlmoon/changedetection.io/wiki/Microsoft-Windows

2. urlwatch
   能力：Python 命令行抓取、过滤、差异检测、报告；可选浏览器任务。
   许可证：BSD 三条款。通常由外部调度运行，适合轻量页面列表。
   决策：参考其过滤与差异处理方式；第一期不再引入一套完整 CLI 和缓存体系。它不提供现成的金融竞争关系与事件数据库。
   来源：https://github.com/thp/urlwatch
   来源：https://github.com/thp/urlwatch/blob/master/COPYING
   来源：https://urlwatch.readthedocs.io/en/latest/jobs.html#browser

3. Playwright Python 与 Crawl4AI
   Playwright：浏览器自动化库，Apache-2.0，支持 Windows。建议作为 JS 页面后备抓取器；普通网页仍走现有 HTTP 通道。
   Crawl4AI：Python 抓取与内容提取工具，仓库列为 Apache-2.0，支持浏览器、Markdown 与结构化提取。可替代自行封装的一部分浏览器抓取代码，但要检验输出能否保留原始证据、表格结构与定位。它的本地开源库不等于其云端搜索服务。
   决策：第一期选 Playwright；需要更广泛正文提取时，再对同一组真实网站比较 Crawl4AI。二者不同时成为必装依赖。
   来源：https://github.com/microsoft/playwright-python
   来源：https://playwright.dev/python/docs/intro
   来源：https://github.com/unclecode/crawl4ai
   来源：https://github.com/unclecode/crawl4ai/blob/main/LICENSE

4. Rival
   能力：竞品档案、页面扫描、历史变化、情报摘要和只读 MCP。
   许可证：MIT。依赖 Next.js、PostgreSQL/Prisma 和 Tabstack API key；竞争者由配置定义。
   决策：借鉴“竞品档案—页面—扫描—差异—摘要”的产品组织方式。整体引入会增加独立应用栈和服务依赖，当前没有必要。官方功能说明也不能证明它已解决金融主体消歧、业务范围竞争判定或历史时点证据问题。
   来源：https://github.com/tessak22/rival

5. Laksh-star/competitive-intelligence
   能力：使用 CocoIndex、Tavily 与 LLM 提取竞争情报，提供事件研究流程。
   许可证：MIT。真实联网模式需要 PostgreSQL、Tavily 和模型 API；无凭据样例模式使用本地样例材料。
   决策：可借鉴事件结构和研究查询方式，不整体替换 V4.1；样例模式不计真实联网能力。
   来源：https://github.com/Laksh-star/competitive-intelligence

6. Firecrawl
   能力：通用网站抓取与提取，主要许可证 AGPL-3.0，部分 SDK 等另有许可证。
   当前自托管文档涉及 API/worker、浏览器和多个后台服务。
   决策：当前单机规模不作为默认组件。若未来需要集中抓取服务，再评估运行成本、证据保存和版本对应的许可要求。
   来源：https://github.com/firecrawl/firecrawl/blob/main/README.md
   来源：https://github.com/firecrawl/firecrawl/blob/main/SELF_HOST.md

任何实际采用的第三方依赖都应锁定版本、记录来源与许可证，保留所需声明。以上推荐是与当前项目匹配程度的架构判断，不是对全部开源项目的穷尽评价。

三、端到端流程

目标研究池
  → 企业与业务档案
  → 竞争关系候选发现
  → 身份、竞争范围与证据确认
  → 生成有界监测池及来源清单
  → 复用采集队列并保存原文/网页快照
  → 正文及结构化字段变化检测
  → 竞争事件提取与归并
  → 按竞争范围关联目标公司
  → 证据简报、待核验队列、覆盖缺口

原文取得、竞争关系识别、事件提取、目标关联、研究解释分别记录完成状态。某一阶段失败不能把其他阶段的结果一并报成功，也不应阻塞无关来源。

有两个相互独立的入口：
A. 已知竞争者：配置或人工确认关系后立即进入持续监测。
B. 未知竞争者：从现有原文和可用发现渠道提出候选，经过证据确认再进入正常监测。

第一期先打通 A 的完整闭环，同时交付 B 的候选生成和审核接口。外部搜索服务是可插拔依赖，未配置时保留基于现有资料的发现能力，并明确跨网站发现的缺口。

四、企业身份和竞争关系

企业主体与证券分离。现有 SEC 公司继续使用 sec:<CIK> 身份，不重编旧记录。未上市公司、外国公司、子公司和品牌使用内部稳定身份，并保存与现有 company_id 的映射；不伪造 CIK 或股票代码。

主体档案至少包含：entity_id、类型、正式名称、带来源的别名、国家/注册地、已验证官网、可选外部标识。股票代码另带交易所和有效期。品牌归属、母子公司关系单独记录有效期与证据，不能只凭名称相似或共用域名合并主体。

竞争关系至少包含：
edge_id、target_entity_id、peer_entity_id、relation_type、product_or_business、geography、customer_segment、overlap_basis、evidence_refs、evidence_status、review_status、valid_from、valid_to、review_due_at、created_at、supersedes。

relation_type 可取直接竞争、替代产品、潜在进入者等。供应商、客户和合作伙伴仍是另一类关系；同一主体可同时具有多种关系。

evidence_status 区分“来源明确陈述”与“基于业务重叠推断”；review_status 区分候选、确认、拒绝和待复核。确认的具体规则与执行人/规则版本必须可查，不能把模型置信度高直接当成已确认事实。

未知地区、产品或客户范围必须保存为 unknown，不能解释成全球、全部业务或全部客户。同一行业代码、财务可比公司名单、新闻中共同出现，都只能帮助提出候选。

候选确认允许两种证据路径：来源明确点名竞争关系；或者双方公开业务材料足以支持指定市场内的重叠，再经审核确认。无需要求所有公司都在年报中互相点名。

旧年报中的竞争关系应标明证据年份和复核到期状态。复核超期不能自动推断竞争已结束；新出现的公司也不能追溯套用成过去一直存在的竞争者。

五、来源发现、监测池和初始化

保留研究目标池 target_universe，另建 peer_watchlist。竞争对手加入采集范围，不自动进入投资目标池。

初始建议上限为每个目标 5 个核心对手、10 个观察对象，全局 30 个去重对手；这些是可调运行预算，不代表现实中只有这些竞争者。达到上限时展示未纳入候选和原因，不静默丢弃。

默认只扩展一层关系；不继续递归抓取“竞争对手的竞争对手”。同一对手服务多个目标时，只建一套主体、来源和原文记录，保留多条关联原因。取消某个目标的关注不能删除其他目标仍使用的监测任务。

每个来源 endpoint 保存：所属主体、URL、渠道类型、入口发现证据、官方/第三方属性、采集方式、地区/语言/货币环境、选择器配置版本、检查频率、最后成功时间、下次到期时间、失败原因、历史深度和预算。

候选入口优先来自已取得申报中的官网、已验证官网中的 IR/新闻/产品导航、RSS 与 sitemap；允许配置补充。人工输入 URL 不应被自动标为官方，需保留来源属性与校验状态。搜索摘要只作为线索，未取得正文时不计完整事实证据。

支持的渠道与用途：
1. SEC/现有申报与 IR：业绩、指引、业务描述、订单、投资、风险与重大事项，复用现有适配器。
2. 官方新闻中心和 RSS：产品、市场进入、合作、订单、产能、并购，新增通用配置化入口。
3. 官方产品页、价格页、服务条款、更新日志：做前后快照与字段差异。
4. 监管公告、公开招投标与客户公告：通过独立适配器补充验证；未实现的市场逐项报缺口。
5. 专利、招聘、开发者文档、公开行业统计：第二阶段按行业启用，作为各自类型的观察信号，不默认等于技术突破、扩产完成或市场份额提升。
6. 获授权新闻、行业研究和搜索接口：可插拔。没有授权或 API 时明确缺少依赖，不模拟接通。

新对手优先复用已有原文。初始化取得支持关系判定的最新业务材料和配置回看窗口内公告；产品与价格页先建立当前基线。需要长期财务比较时再调用现有分批历史初始化。今天第一次抓到的网页不能伪装成历史网页。

至少支持一个没有证券代码的企业通过“稳定主体身份＋经核实官网入口”进入正式监测流程。外国交易所和当地申报渠道未实现时，可以监测官网，同时明确法定披露渠道缺口。

六、变化检测与事件模型

原文哈希变化、正文变化、业务字段变化、研究相关事件是四种不同结果。保留原文版本，但不因广告脚本、时间戳、导航标题、追踪参数变化制造竞争事件。

先用规则处理正文区域、表格、价格和页面结构，再对语义变化调用可配置模型。过滤规则必须保留数字、正负号、单位、否定词和比较对象。过滤器/选择器升级后可从原文重解析。

网页观测上下文固定并留存：国家/语言、货币、登录状态、必要的地区选项。不同地区、套餐、规格、数量、税费和付款周期的价格不能直接算涨跌。价格记录区分挂牌价、促销价、会员价和实际成交价；网页挂牌价不能代表全公司的平均售价。

首次快照仅产生 baseline。后续发现差异但没有官方发布日期时，变化时间记录为“上次成功观察与本次观察之间”，不能把抓取时刻当实际发生时刻。抓取失败、登录墙或空页面不能解释为产品下架。

第一期事件类型：业绩/指引更新、产品发布/退出、定价/促销/合同条款变化、订单/客户/合作、产能/渠道/区域进入、重大监管/并购事件。来源无法可靠提取某类型时保留候选，不硬凑数字。每个类型维护“已实现提取器、真实来源样本、未支持结构”清单。

competitive_events 至少包含：
event_id、actor_entity_id、event_type、action、object、business_scope、geography、status、event_time/precision、publication_time/precision、first_observed_at、processed_at、old_value/new_value及口径、evidence_refs、extraction_method/version、verification_status、revision_of。

事件 status 区分宣布、计划、签约、完成、取消和更正。“计划建厂”不能变成“产能已增加”。来源写“赢得订单”并不证明目标公司丢掉同一订单。

每个 evidence_ref 包括原文/快照版本、URL、定位和必要短摘录。校验摘录确实存在于对应版本；数据明确区分来源声称与独立核验。模型输出保存模型标识、提示词版本、输入哈希和结构校验结果；缺模型依赖时规则采集继续，语义任务显示等待依赖，不报零事件且成功。

七、事件关联、比较与输出

competitive_event_links 单独连接事件与目标：event_id、target_entity_id、edge_version_id、matched_scope、mismatch_or_unknown、relevance_reason、review_status、processed_at。

一条事件可以关联多个目标，但每个关联必须说明对应业务、地区和竞争关系证据。地区明确不重叠的事件不自动进入核心简报；范围未知的事件进入待判定区，不能自动扩张成全公司影响。

优先级由规则可解释地综合业务重叠、事件具体程度、来源质量、时间与关注级别，保留各项依据。不要把一个无校准的“0.93”包装成真实影响概率。

研究解释放在可选 analysis_hypotheses：机制、支持证据、反向解释、缺失信息、待验证问题。默认不生成收入/利润增减估计。对手增长可能来自行业扩张，也可能来自份额变化，应根据证据分辨。

财务/经营对比直接引用现有 financial_facts 和新增事实记录，比较前核对期间、地区、币种、单位、业务边界、GAAP/非GAAP和指标定义。口径不一致时并列展示差异，禁止强行排名。市场份额需要可核验的市场总量及一致范围，不能用对手的增长率代替。

至少输出四个可读视图，同时提供 JSON：
1. 竞争关系表：谁、在哪竞争、证据和复核状态。
2. 变化简报：发生了什么、与哪个目标业务有关、前后证据。
3. 覆盖缺口：哪些对手/渠道没有检查成功、过期、待提取或未配置。
4. 待核验清单：身份歧义、关系候选、冲突事实、无法解释的变化。

简报条目示例，以下公司和数值均为假设：
“B 公司宣布计划于 2028 年把德国工厂年产能从 8 GWh 提至 12 GWh。与 A 公司相关的范围为欧洲固定式储能电芯，依据已确认竞争关系 R1。当前状态为宣布计划，未验证投产。证据为公告版本 D1 的指定段落。需要继续观察投产进度、产品规格及需求变化。”

八、去重、修订和时间证据

原文层：复用 raw_blobs/raw_retrievals。同原文由多个入口取得时保留获取流水和来源地址。
事件层：保留多份来源主张，再将明确描述同一事项的材料关联到一个事件。归并依据可以使用发行人事件号、合同/项目/产品身份和具体行动；标题相似或同日发布不足以合并。归并可撤销。
报告层：以目标＋事件＋重大事实版本去重。多来源转载不重复刷屏；合同金额或状态真实更正需要重新呈现。同一天的两个不同合同必须保留为两个事件。

时间至少区分事实发生/生效、来源公开、系统取得、系统处理；关系另有有效区间。未知公开时间保持未知。后处理不得追溯改写“当时系统已知”。

历史查询同时约束关系、事件、关联和所有引用证据。不能拿当前竞争关系去拼过去的事件，然后称为当年的可用信息。沿用 V4.1 三种时间过滤，并保留其历史机器状态重放的既有限制。

关系失效、更名、身份纠正、事件修订、撤销归因均追加版本。纠正错误关系后可重跑受影响关联，不删除原始证据或重写旧简报。

九、调度、预算与本机运行

继续使用现有唯一 Windows 任务，北京时间 09:00、20:30、23:30；登录补采和五分钟轻量检查维持原义。

建议策略：核心竞争者的事件入口每日三次；观察对象每日一次；竞争关系候选发现和官网入口复核每周一次，遇到新年报、并购或业务变动再提前复核；决策前可刷新指定目标及其核心对手。

每日三次表示离散观察，没有实时或固定最长延迟保证。电脑关机或来源失败的缺口必须显示。普通网页在两次抓取之间出现又消失的内容可能无法恢复；补采不能宣称补齐所有临时变化。

竞争任务使用独立额度但受现有总预算约束，先确保目标公司原有采集，再公平处理核心对手和观察对象，防止低优先级永久饥饿。建议首轮新增浏览器并发 1、单页超时 45 秒、每轮最多 20 次页面导航和 30 次模型调用；这些是待实测调整的上限，不能绕过总时长、来源速率和请求限制。

浏览器导航数与底层 HTTP 请求数分别记账，不能把一次浏览器导航当成仅一次网络请求。对每个域名限速；请求失败保留有限重试和退避。采集只能使用配置允许的公开/授权来源，发现 URL 要验证协议、域名与重定向范围。

记录每次运行实际使用的目标池、竞争关系版本、有效监测池、endpoint 清单、配置哈希和预算。任务中途配置改变不影响已经冻结的运行范围。

网页渲染或模型处理超时不拖死后续采集。竞争分析设独立持久任务表和进度，可以下一轮继续，也可以从原文离线重跑；复用同一进程入口和执行锁，不新增常驻 worker、另一套 Windows 调度或自动购买云服务。

十、与 V4.1 的代码接入

拟新增 equity_data/competition 包，最小职责如下：
entities.py        主体映射、别名、品牌/母子公司和身份审核
relations.py       竞争范围、证据、版本和确认
discovery.py       现有资料候选发现与可选搜索入口
watch_planner.py   target/peer 范围、endpoint、去重和预算
change_detector.py 正文及结构化字段差异、基线与噪声判断
events.py          事件提取、证据验证、状态与修订
linker.py          事件到目标业务的关联
jobs.py / runner.py 派生任务持久化、幂等与续跑
queries.py         当前/历史查询、证据追踪
reports.py         关系表、简报、缺口、待核验输出

新采集方式仍在 equity_data/adapters 下按 BaseAdapter.discover/acquire/parse 接入；网页 adapter 可配置 HTTP 或 Playwright 后备。第三方变化服务未来也遵循此接口边界。

新增逻辑数据集建议为 entities、entity_links、competition_edges、competitive_events、competitive_event_links，可选 analysis_hypotheses；另有 watch_endpoints、competition_jobs、review_actions 和报告去重状态。允许复用现有 records 版本容器，不强制每个逻辑集单独建物理表。

关键代码约束：
1. universe.py：保留旧 SEC 身份；证券解析与通用企业身份层分离，不能把无 CIK 企业送进只接受 SEC 身份的适配器。
2. local_control.py 的 base_payload、local.py 的 active_config、initialization.py：将竞争配置和关系版本纳入冻结请求。
3. machine.py、engine.py：effective_universe 和 endpoint 范围进入范围指纹，防止目标池变了但沿用旧完成状态。
4. 现有 engine._execute() 将非 discover 任务按 acquisition/reprocess 处理。竞争分类和关联使用独立派生任务表，不直接伪装成现有抓取任务。
5. store.py：复用追加版本与 supersedes；派生结果使用独立来源/资源命名空间及输入 manifest。
6. adapters/base.py 的 persist_observations() 会对同来源/资源未再输出的旧自动字段产生 tombstone。不能把竞争派生输出单独传入同一旧资源处理流程，意外撤销已有财务事实。
7. registry.py：采集 data_types 与派生输出能力分开声明，分析成功不冒充新外部渠道接通。
8. cli.py、machine_reports.py、coverage.py：增加查询与分阶段状态，不改变旧库存/覆盖指标含义。

建议接口契约，具体命名可调整但语义应保留：
discover_candidates(target_id, evidence_scope, budget) -> candidates + evidence + gaps
review_relation(edge_id, decision, reason, evidence_refs) -> new_edge_version
plan_watches(target_ids, relation_snapshot, config_snapshot) -> deduplicated_plan
process_competition(input_versions, extractor_version, budget) -> events + pending + gaps
link_events(event_versions, relation_snapshot) -> target_links + unresolved
query_competition(target_id, as_of, known_at, processed_at) -> evidence_bundle

建议提供 competitors discover/list/review、competition refresh/process/query/trace/status 等 CLI 能力。读取查询不隐式联网；refresh 明确返回 request_id，queued 不等于已经刷新完成。只读 MCP 可在第二阶段包装查询接口，第一期 CLI/JSON 足够。

十二、分阶段实施

阶段 A 交付可用闭环：
主体与竞争关系模型、可审核的候选、人工确认/配置入口、范围冻结、SEC/IR 复用、官方新闻/RSS及配置网页监测、快照差异、第一期事件提取与拒绝状态、目标关联、CLI/JSON/可读报告、去重及历史证据查询。

无证券代码主体、关系范围、事件证据与去重必须在 A 阶段具备。某网站动态渲染确实需要时使用 Playwright。模型未配置时交付规则能力与待处理状态，不宣称完整语义提取已验收。

阶段 B 提高发现和分析深度：
可插拔搜索、行业规则包、专利/招聘/招投标适配器、可比经营指标、关系复核提醒、只读 MCP 和可选 changedetection.io 适配。

优先完成 A，避免同时建设图数据库、向量库、分布式任务系统和大型仪表盘。SQLite 中的关系、证据和版本足以承载首期规模；规模指标表明需要时再迁移。

十三、验收设计

验收关注真实关系和可用事件，测试数量、下载数量与候选片段数量不能单独代表交付完成。

先冻结提取规则、提示词、代码和验收定义，再使用未参与调试的目标与资料。相关转载和同一事件的多个版本应放在同一个测试集合，避免开发样本泄漏到保留样本。

建议最小真实验收集：3 个跨行业目标，至少 6 条经人工判定的有证据竞争关系；包含一个无证券代码主体、一个品牌/母子公司情形、一个仅局部业务或地区竞争的情形。至少一个目标在代码冻结后通过配置加入。此规模只验证通用流程，不证明全市场覆盖。

建议另建独立事件评测集：至少 30 个相关事件和 30 个负例/歧义/噪声案例，覆盖不少于 4 类事件和 2 类来源；清晰标记真实历史样本与合成故障样本。未达到规模或某类型没有真实证据时，按实际能力交付，列明该部分尚未通过。

首期建议验收门槛为：在上述固定、有标签、已覆盖来源样本中，核心简报事件精确率至少 90%，相关事件召回率至少 80%；同时逐项报告分子、分母、拒绝、漏报与待核验，不把模型拒绝从召回分母剔除。这些是设计目标，不是当前项目或开源组件的实测结果。

以下为必须满足的行为约束：
1. 新目标、新对手通过配置接入，不修改生产公司分支或写入答案。
2. 同名企业、代码重用、品牌与母公司不会静默错合并；不确定时停留在待确认。
3. 仅同业/共同出现的公司不会自动成为已确认竞争关系。
4. 产品/地区不重叠的硬负例不进入核心目标简报；未知范围有明确标记。
5. 每条核心事实都能追溯到原文版本、位置和来源；首次快照不会伪造价格变化。
6. 计划与完成、挂牌价与成交价、季度与全年、不同货币等不被混用。
7. 导航、脚本、空白变化不造成业务事件；403、登录墙和页面抓取失败不当成产品退出。
8. 同一事件多处转载只出现一条核心事件；同日不同合同不被合并；更正保留历史并显式更新。
9. 同一对手被多个目标关注只采一次；取消一条关系不会误删其他目标的来源。
10. 重跑、补采、重解析幂等；模型失败与来源失败独立续跑，不导致正常来源反复下载。
11. 修改身份或竞争关系后可重算关联，旧时间查询不使用后来才确认的关系和事实。
12. 竞争模块关闭时原流程行为保持一致；原财务记录不被派生处理误撤销；迁移和备份恢复可回退。

覆盖报告分开给出：已确认对手中有健康来源的比例、配置入口的应检查/成功/失败/延后数、可枚举清单内的资料取得率、评测样本的事件准确率/召回率、来源公开至取得及取得至处理的延迟。日期精度不足时不计算虚假的分钟级延迟。

不得声称“全部竞争信息覆盖率”。开放互联网没有可直接取得的完整分母；成功请求也不代表该网站披露了所有重要事项。

自然运行观察另列：三次日常轮次、关机/休眠后的补采、自然新披露和修订。受控回放可先验证逻辑，尚未自然发生的情况保持待观察，不能冒充完成。来源未变化时，不为完成验收制造所谓真实新事件。

十四、实施 agent 的交付要求

按本架构先完成阶段 A。开工先核对当前项目版本、现有文档和未提交改动，保护已有修改。以增量数据迁移和开关接入，先在副本/隔离运行目录验证，再按既有运维流程接入原调度；保留原库和恢复路径。

交付：代码与依赖清单、配置样例、数据契约、迁移/回退说明、原文与快照证据、关系审核记录、冻结保留样本结果、重复运行证明、覆盖及缺口报告、日常操作说明。

报告开头直接说明可用范围：哪些目标/对手、哪些渠道、哪些事件类型、哪些只到候选、哪些需要授权/模型/人工确认。附一份可直接供研究 agent 查询的真实证据包，展示“对手事件→目标业务关联→证据→未知事项”。

验收完成的依据是可复用的闭环和诚实的能力边界。未取得的资料、无法确定的竞争关系与未验证的财务影响，都应作为系统输出的一部分。
