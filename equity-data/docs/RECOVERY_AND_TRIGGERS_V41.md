# V4.1 恢复范围与额外采集触发

恢复和触发控制位于 `equity_data/local_control.py`。本轮只保留一个本机执行者；OS 锁取得以后，才允许恢复旧 `running` 请求。

## 异常恢复

同逻辑范围有后继请求时，先在同一个 `BEGIN IMMEDIATE` 事务内，把旧请求和后继请求的最早 `window_start_hint`、`resume_scope_ids` 并集及恢复请求链写到后继，再把旧请求标为 `interrupted`。转交事件、旧请求状态和后继内容一起提交；任何一步失败会全部回滚。

没有后继时，原请求回到 `pending`，窗口保留。两种路径都不依赖来源 scope 已经落库，所以在第一次资料发现之前崩溃也能恢复较早补采范围。连续中断保留原始最早窗口和完整请求链。

股票池、来源、信息类型、初始化标识及历史范围属于请求身份。`window_start_hint`、`resume_scope_ids` 和 `_local` 恢复元信息不改变身份，但不同股票池、来源或信息类型不能合并。

## 五分钟检查和额外采集

五分钟检查只枚举到期计划、查看已经排队工作，以及检查有明确任务证据的有限续跑；没有这些原因时，不发起全源采集。请求事件保存原始 reason、标准 category、触发时间，以及对应计划时点或上次请求。

标准类别是正常计划、错过计划补采、未完成工作续跑、有限失败重试、手动刷新、历史修订检查；历史初始化有单独类别和批次账本。

`build_continuation(store, run)` 根据该次请求的已持久化 source scopes 和实际未完成任务生成收据。等待下载的 pending/budget 工作可以续跑；限流、认证、权限、临时网络错误要同时满足底层退避时间和本机重试间隔，且不超过既定次数。只选择有资格继续的来源，并转交它们的 scope IDs。权限冷却和资源重试上限仍由底层队列控制，调度不能重置。

部分字段未解析、语义候选、未知 IR 入口、缺少依赖或 unsupported 不能仅因为报告为 partial 就触发全源重跑。原文已取得而只剩解析问题不会自动变成网络重试。旧请求没有任务级续跑收据时，保留历史且不回填猜测的重试理由；下一正常计划或用户手动刷新仍可检查。

初始化工作由单独的初始化账本分批推进，`initialization=True` 请求不会再被一般 partial 重试重复加入。

## 证据与限制

- `reports/v4_1/recovery-before-local_control.py`：修复前代码快照。
- `reports/v4_1/recovery-before.json` / `recovery-after.json`：同一合成异常场景前后，修复前最早窗口丢失，修复后窗口及 scope 保留。
- `tests/test_local_recovery_v41.py`：有/无后继、较早/较晚日期、连续中断、scope 未建立、不同范围、事务中途失败及精确重试行为。
- `reports/v4_1/recovery-regression.xml`：本模块与已有本机回归共 30 项通过。
- `reports/v4_1/trigger-audit-before.json` / `trigger-audit-after.json`：真实历史只读审计及新策略判断。

恢复缺陷是合成输入复现；未据此断言真实库已经发生历史窗口漏采。受控异常、自然整机重启、自然登录或休眠恢复是不同证据，本轮回归不替代未来自然运行观察。
